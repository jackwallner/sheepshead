# Review of the state machine audit, 2026-11-06

Independent review of `state-machines-2026-11-06.md` and its repro suite. Every claim was re-derived from the code at HEAD (`2be9d63`); the audit's own reasoning was not used as evidence. The audit names commit `f68765f`, which does not exist in this repository's history, so its line numbers were checked one by one against HEAD (they match). Nothing in the app was changed.

Summary: 6 bug claims. 1 CONFIRMED (C2), 1 CONFIRMED-MINOR (B1), 3 NOT A BUG (B2, C1, C3), 1 UNVERIFIED (C4). False-positive rate 3 of 6 (50%); of the 5 claims that could be decided, 3 were wrong (60%). The audit's top two "proved" bugs are one minor bug and one documented rule; its only real user-facing bug (C2) was filed as code path only and ranked fourth.

## Test results

Rerun once on `gh-sim` (GitHub run 42302946399, Xcode 27.1, iPhone 17 on iOS 27.2), with the audit's suite copied into `SheepsheadUITests` plus one reviewer test, then removed again. The target still needs the audit's per-call `NSPredicate` workaround at `FlashcardDeckUITests.swift:74-77` to compile; it was applied for the run and reverted.

- `testControlOneAnswerLocksInNothing`: PASSED (chip "0 of N locked in"). Matches the audit.
- `testUndoThenReanswerDoesNotCountTwice`: FAILED, `("1") is not equal to ("0")`. Matches the audit. Its preconditions held (Undo offered, header back to "0 of"). This proves the behaviour; the expectation is reasonable for a control labelled "Undo last answer" (`FlashcardDrillView.swift:88`), though no doc comment states it.
- `testReviewMistapUndoLeavesWrongAnswerInStats` (reviewer, the realistic route: pick "52 cards", Next, Undo, pick "32 cards", Next, Settings > Your Progress): FAILED, `("50%") is not equal to ("100%")` with "2 answered". This is the symptom a real Undo user sees.
- `testClosingFixMyMistakesEarlyScoresOutOfWhatWasAnswered`: FAILED, "1/3". Matches the audit, and shows the documented `gradedTotal` rule working as written (see B2). Its preconditions held.

## What survived, ranked

1. C2: a lapsed member's game night reminder keeps firing weekly and cannot be turned off in the app. Highest reach of anything in the audit, and the only one that acts on a user outside the app. Fix direction: clear the flag wherever a resolved non-member is seen, not only on a change (launch, foreground, and the non-member branch of `consumePendingDestination`).
2. B1: Undo leaves the undone grade in the stores. Minor: a mistap leaves a phantom miss and a review item due the next day; the "locked in" inflation needs an unlikely sequence.

The audit's ranking (B1, B2, C1, C2, C3, C4) should be C2, B1; B2, C1 and C3 drop out and C4 waits on C2.

## Method changes

1. Quote the promise and read its neighbours. B2's cited comment covers only zero answers, and the scoring rule it was said to break is written two lines above `gradedTotal`. A claim should quote the exact sentence it relies on, and the reviewer should read the doc comments on every property the fix would touch.
2. Route the bug through the user's motive, not just through reachable taps. Nobody undoes a correct answer; they undo a mistap. Testing the mistap path would have shown the real symptom and the real (small) impact.
3. Resolve vendor behaviour from vendor source. C2 was left as "depends on RevenueCat's cache"; the SDK version is in `Package.resolved` and the 3-day grace rule is twenty lines of public code.
4. Check the identity model and Apple's own guards before claiming a sell-to-member risk (C3): anonymous ids, no `logIn`, and StoreKit refusing to double-sell.
5. Separate app state drift from an OS setting the user changed on purpose (C1).
6. Check impact arithmetic (B2's review-prompt claim) and keep one classification per behaviour (B2 versus P5).
7. Pin a commit that exists. `f68765f` is not in this repository.
8. A failing UI test proves behaviour, not a bug. Each failing assertion should name the promise it encodes, and the review should ask whether that promise is written anywhere.
