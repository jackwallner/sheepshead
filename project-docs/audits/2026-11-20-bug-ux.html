Bugs, worst first

B1

Streak resets or counts twice when the phone changes to a time zone west of where the last drill was done

mediumconfirmedstate
Impact

A player with a streak who travels west by even one hour, or whose phone changes zone, loses the streak or gets a free extra day. The streak chip on Home, Your Progress and the completion screen shows the wrong number. Moving east is not affected.

How it happens
  1. On a phone set to US Eastern, finish a drill on Monday evening. The app stores progress.lastActiveDay as Monday 00:00 Eastern (05:00 UTC).
  2. Fly to the US West coast (or change the time zone setting to Pacific). Relaunch the app.
  3. The stored instant now reads as Sunday 21:00 Pacific, so the stored day is Sunday.
  4. Open Home on Tuesday. The streak chip shows 0 (gap Sunday to Tuesday is 2). Finish a drill: the streak restarts at 1 instead of growing from Monday to Tuesday.
  5. The mirror case: finish a drill Monday in Eastern, land in Pacific the same Monday evening and finish another. The stored day reads Sunday, so Monday counts as the next day and the streak goes up by 1 for one calendar day.
Where
Shared/Services/ProgressStore.swift:87Shared/Services/ProgressStore.swift:91Shared/Services/ProgressStore.swift:105Shared/Services/ProgressStore.swift:76
Suggested fix

Store the last active day as a Gregorian day string (like MasteryLedger.dayKey) or store the day's components with the zone, and compute the gap from those instead of re-running startOfDay on an old instant.

Evidence
let today = calendar.startOfDay(for: now)
let last = defaults.object(forKey: Keys.lastActiveDay) as? Date
if let last {
    let lastDay = calendar.startOfDay(for: last)
    let gap = calendar.dateComponents([.day], from: lastDay, to: today).day ?? 0
    ...
defaults.set(today, forKey: Keys.lastActiveDay)

The stored value is a Date (an instant) that is midnight in the zone the phone had at the time. Later it is passed through startOfDay again in whatever zone the phone has now. For any zone west of the original one that instant falls on the previous calendar day, so the day gap is off by one. MasteryLedger and the Minute already use Calendar.gregorianLocal day strings, which do not have this problem; ProgressStore does not. DST alone does not trigger it (same zone id, so the instant maps back to the same day).

Checked by: TimeStateProofTests/testStreakNotCountedTwiceForOneDayAfterFlyingWest failed (2 is not equal to 1) and testStreakSurvivesConsecutiveDaysAfterFlyingWest failed twice (currentStreak 0 instead of 1, streakCount 1 instead of 2). gh-sim run repo-mbpro3a5b2-1120-133659-1754.

Not proven: The tests seed the stored Date as the app would write it in Tokyo and read it in the runner's UTC calendar, because Calendar.current cannot be switched inside a unit test. Whether a running (not relaunched) app picks up the new zone was not observed; after a cold launch it does.

B2

A paying member with an old RevenueCat cache can be asked why their membership ended

mediumplausibleentitlement
Impact

A customer who just converted or renewed is shown a 'why did you leave' feedback sheet, and may type a reply that lands in the churn data as a real departure. It reads as the app not knowing they paid. The locks also flash on for that second. The game night reminder was fixed for this exact cache problem on Nov 6 (lapseConfirmed), but the churn path was not.

How it happens
  1. Start a free week on day 1 and open the app once (the app stores an 'active, trial' snapshot).
  2. Do not open the app again until after day 8. The trial converted and Apple charged the card.
  3. Open the app. start() applies RevenueCat's cached record from day 1. Per the repo's own verify doc, a cache older than 3 days is judged against today with the expiry it last read, so it reads 'not active'.
  4. apply() calls observe(). The stored snapshot is active, the new one is inactive, so a trialLapsed (or paidLapsed) churn moment is stored and published.
  5. Home waits 0.9 seconds, then shows 'Your free week ended. What held you back from keeping Sheepshead+?'. If the network record has not arrived by then (cellular, slow, offline), the sheet appears for a member who just paid.
  6. Same thing for a monthly or yearly subscriber who last opened the app before a renewal.
Where
Shared/Services/SubscriptionService.swift:381Shared/Services/SubscriptionService.swift:398Shared/Services/SubscriptionService.swift:450Shared/Services/MembershipTransitions.swift:46Sheepshead/Views/HomeView.swift:214
Suggested fix

Only let observe() record a transition to inactive when lapseConfirmed would be true for that record (answered after the launch cache or within freshBaselineAge). Skip observe() for the launch cache when it says inactive.

Evidence
// MembershipTransitions.swift
guard let previous, previous.isActive else { return nil }
if !current.isActive {
    return previous.isTrial ? .trialLapsed : .paidLapsed
}
// SubscriptionService.swift observe()
if previous == nil, now.timeIntervalSince(answeredAt) > Self.freshBaselineAge { return }
...
guard let moment = MembershipTransitions.churnMoment(from: previous, to: current) else { return }
defaults.set(true, forKey: churnAskSpentKey)
defaults.set(moment.rawValue, forKey: pendingChurnKey)
pendingChurnMoment = moment

The freshness guard in observe() only protects the first-ever record (previous == nil). Once a baseline exists, any inactive record is trusted, including the launch cache that apply() feeds in at SubscriptionService.swift:104. lapseConfirmed already exists to tell a cache answer from a network answer but observe() does not use it. The later network record (active and renewing) does call resetsAsk, which clears the pending moment, so the prompt is only avoided if the network answers inside Home's 0.9 second wait (HomeView.swift:217).

Checked by: The app half is shown by test: testStaleCachedInactiveRecordDoesNotQueueChurnQuestion failed, so a not-active record answered 4 days ago queues the question (run repo-mbpro3a5b2-1120-133659-1754). That RevenueCat hands back such a record at launch comes from the Nov 6 notes, not from a phone.

Not proven: Not run on a device. Relies on the Nov 6 verify doc's reading of purchases-ios 5.80.3 (stale cache re-judged by the local clock) and on the network record arriving later than 0.9 seconds or not at all.

B3

Home keeps yesterday's 'Today's session is done' card and Minute badge after midnight

mediumplausibleedge
Impact

The reminder asks for a drill and the screen it lands on says there is nothing to do today. The daily habit loop is the retention feature, and the next-day return from background is the most common way people come back.

How it happens
  1. Finish Get Started and the Sheepshead Minute in the evening, then leave the app backgrounded (not force quit).
  2. Next morning the daily reminder ('Time for a quick drill') fires. Tap it.
  3. Home returns to the foreground. The card still reads 'Today's session is done. A fresh mix lands tomorrow.' with no Get Started button, and the Minute tile still says 'N/5 today'.
  4. The card only corrects after something invalidates Home (opening a room and coming back, a sheet, a store change).

Suggested fix

Add a day-change trigger Home observes: a @State today refreshed on scenePhase == .active and on NSCalendarDayChanged / UIApplication.significantTimeChangeNotification.

Evidence
if progress.quickSessionCompletedToday() {
    getStartedDoneCard
} else {
    getStartedCard
}
// SheepsheadApp.swift
.onChange(of: scenePhase) { _, phase in
    guard phase == .active else { return }

Both values are computed from Date() inside body, but nothing publishes at day rollover. The only scenePhase handler flushes feedback. Home observes records, ledger, minuteStore and settings, none of which change on foreground. Tapping the plain daily reminder carries no route, so consumePendingDestination does nothing either. A push and pop from Home flips homeOnScreen and redraws, which hides the problem for people who navigate first.

B7

Timed Challenge clock stops while the app is in the background, so a break or a lookup is free time

lowplausiblestate
Impact

The best Timed Challenge score can be built with unlimited thinking time or lookups, so Best is not comparable to a real 90 second run. A phone call mid-run costs the player nothing, which hides the problem from honest players but makes the score meaningless for the ones who notice.

How it happens
  1. A member opens Home, then Timed Challenge. The 90 second clock starts at once.
  2. Answer a question, then switch to another app (or take a call) for five minutes.
  3. Come back. The clock shows about one second less than before you left, and the run continues.
  4. Finish the run. The score is saved as the best challenge score.
Where
Sheepshead/Views/Drills/PracticeRunView.swift:233
Suggested fix

Store an end Date when the run starts, and compute secondsRemaining from Date() each tick (or finish the run when the app returns after the end date).

Evidence
while secondsRemaining > 0 && !finished {
    try? await Task.sleep(nanoseconds: 1_000_000_000)
    guard !Task.isCancelled else { return }
    secondsRemaining -= 1
}

The countdown counts completed one second sleeps, not elapsed wall time. A sleep that was pending when the app suspended returns once on resume and removes one second. No scenePhase or end-date check exists in the view or its parent (the only scenePhase use is SheepsheadApp.swift:25, feeding FeedbackService).

Checked by: Code reread; no test.

Not proven: Not run on a device. Relies on Task.sleep returning one time after a suspension rather than being cancelled by the system, which is how its deadline based sleep behaves.
